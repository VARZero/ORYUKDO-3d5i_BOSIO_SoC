# 빌드와 검증 방법

## 구성과 작업 디렉터리

현재 SD4·DMA 후보는 `variants/sd4-dma/`, 이전 실보드 기준본은 저장소 루트다.
아래 후보 명령은 먼저 후보 디렉터리로 이동한 뒤 실행한다. 문서 후반의 기준본 명령은 저장소 루트에서 실행한다.
두 소스 목록·Linux 설정·SD 이미지를 혼합하지 않는다.

기존 검증 도구는 Vivado 2022.2, Verilator 5.020, WSL/Ubuntu, RISC-V GCC 13.3.0 및 Binutils 2.42다.
출력은 별도 디렉터리로 만든다. 테스트 스크립트는 `validation/`의 로그를 다시 쓰므로 보존 근거와 구분할 별도 checkout에서 실행한다.

## 게시본 무결성 검사

저장소 루트에서 실행한다. 이 명령은 새 보드 시험이 아니라 소스·증거의 일치 검사다.

```sh
python3 scripts/verify_sources.py
python3 scripts/verify_sd4_publication.py
python3 variants/sd4-dma/soc/board/verify_vendor.py
```

## SD4 후보의 RTL 시험

```sh
cd variants/sd4-dma
export XPM_ROOT=/path/to/Vivado/2022.2/data/ip/xpm
bash software/storage/test.sh
bash software/storage/test_cpu.sh
KFB_NATIVE_BACKEND=1 bash software/storage/test_cpu.sh
```

첫 스크립트는 SD·DMA·PLIC·CSR·부트 오류와 전체 SoC lint를 실행한다.
CPU 시험에는 `riscv64-unknown-elf-gcc` 등이 필요하다. native backend는 실제 보드 bridge/arbiter와 mock DDR를 쓴다.
기존 BOSIO 시험은 같은 후보 루트의 `soc/tools/test.sh`다. 저장된 결과와 새 실행 결과의 경계를 [검증 문서](검증.md)에서 확인한다.

## SD4 커널·이미지 입력

현재 Linux 전체 소스는 [SD4 릴리스](https://github.com/VARZero/ORYUKDO-3d5i_BOSIO_SoC/releases/tag/sd4-dma-20261110-candidate)의
`linux-6.12-sd4-dma-source.tar.gz`, 실제 설정은 후보 `software/storage/linux.config`다.
구형 `scripts/prepare_linux.py`, `scripts/build_linux.sh`, `software/bosio/scripts/build_kernel.sh`는
trace-v2 또는 초기 BOSIO용 경로이며 새 SD4 이미지의 재현 명령으로 사용하지 않는다.

이번 실제 실행 진입점은 후보의 `software/storage/build.sh`다. 다음 로컬 의존성이 남아 있다.

| 입력 | 스크립트가 참조하는 당시 경로 |
|---|---|
| 진단·BOSIO를 포함한 Linux 기반 트리 | `/var/tmp/oryukdo-boayo-boottrace-v1/linux` |
| 보존할 root와 커널 설정 | `/var/tmp/oryukdo-boayo-native-v2-final/root`, `kernel/.config` |
| initramfs 목록 생성 도구 | 후보의 형제 작업본 `../bosio-linux-sw/software/boayo/root_list.py` |
| 컴파일 도구 | `riscv64-linux-gnu-`, make, bison/flex, bc, libssl/libelf, dtc |

공개 checkout에는 위 형제 작업본과 전체 userspace 빌드 환경이 자동 생성되지 않는다.
입력을 준비하고 경로를 맞춘 별도 환경에서 다음을 실행한다. 원래의 `/var/tmp` 디렉터리를 무조건 덮어쓰지 않는다.

```sh
bash software/storage/build.sh /별도/새/출력경로
```

명령은 새 드라이버·필요한 커널 설정·`/data` 초기화·이미지를 만든다. 새 바이너리의 바이트 동일성이나 실보드 PASS는 별도다.
Linux를 다시 빌드하지 않고 준비된 **현재 SD4** `Image`, `fw_jump.bin`, `gen3.dts`가 있는 디렉터리로 이미지를 만들 수도 있다.

```sh
python3 software/storage/make_image.py /별도/이미지출력 --firmware /현재/SD4/firmware --data-mib 256
```

이 명령은 이미지 파일만 생성하며 물리 SD 장치를 열지 않는다. 새 ext4 UUID 등으로 최종 이미지 해시는 달라질 수 있다.
보드 기록에는 검증 후 한 쌍의 비트스트림·이미지를 사용한다.

## SD4 후보의 Vivado 구현

Windows에서 후보를 작업 루트로 사용한다. 설치 경로·IP 출력 경로를 맞추고 새 출력 디렉터리를 지정한다.

```powershell
Set-Location variants/sd4-dma
& 'D:/Xilinx2202/Vivado/2022.2/bin/vivado.bat' -mode batch -source soc/board/build_mig.tcl -tclargs D:/build/oryukdo-sd4-mig
python soc/board/run_board.py D:/build/oryukdo-sd4-board --ip D:/build/oryukdo-sd4-mig/kfb_bosio_mig.srcs/sources_1/ip/mig_7series_0/mig_7series_0.xci --strategy area-medium-guarded
```

위 명령은 이전 배선 checkpoint 없이 구현하는 경로이며 기존 성공 결과를 보장하지 않는다.
이번 채택 비트스트림은 `reuse_synth_route.py`가 검증한 합성 결과와 이전 보드 배선 checkpoint를 재사용한 결과다.
전체 합성부터 같은 전략을 쓰려면 `run_board.py --strategy area-medium-incremental --reference /검증된/routed.dcp`를 사용한다.
실제 전체 명령과 로컬 의존성은 [후보 상세 문서](../variants/sd4-dma/README_STORAGE_KO.md)에 있다.
대형 DCP와 생성 MIG는 Git에 포함하지 않았다.

부품 `xc7a200tfbg484-2`, CPU 20ns·fabric 10ns, setup uncertainty 0.300ns를 유지한다.
새 실행은 배선 후 WNS/WHS≥0, TNS/THS=0, 미배선·배선 오류 없음, DRC·CDC·SD 핀 검사로 새로 판정한다.
현재 +0.034ns를 다른 실행의 결과로 재사용하지 않는다.

## 콜드 부팅 검사의 구분

후보 `software/storage/test_actual_loader.py`는 실제 이미지의 RTL 적재 비교다. CPU에서 Linux를 실행하는 시험이 아니다.
`test_qemu_shell.py`는 같은 payload의 QEMU 복구 셸 시험이며 새 SD 장치 모델을 포함하지 않는다.
전체 CPU RTL의 SD→Linux 셸은 아직 PASS로 인정하지 않는다. 장시간 검증을 이번 문서 수정 때문에 재시작하지 않았다.

# 2026-11-08 기준본 빌드 기록

원본 보드 검증 도구는 Vivado 2022.2, Verilator 5.020, Ubuntu/WSL의 RISC-V GCC 13.3.0 및 Binutils 2.42이다. 출력은 항상 별도 디렉터리에 만든다. 기존 실행 중인 RTL 시뮬레이션이나 보드에는 영향을 주지 않는다.

## 기준본: 빠른 검사

저장소 루트에서 실행한다. 쉘 스크립트는 Linux/WSL용이다.

```sh
python3 scripts/verify_sources.py
python3 soc/board/verify_vendor.py
export XPM_ROOT=/path/to/Vivado/2022.2/data/ip/xpm
bash soc/tools/lint.sh
KFB_TLB_UNIT_OUT=/var/tmp/oryukdo-export-tlb bash soc/board/clocksource_debug/run_tlb_unit.sh
```

BOSIO 통합 검증은 `bash soc/tools/test.sh`이다. RISC-V bare-metal 도구가 필요하고 두 장면과 세 seed를 검사한다. 기타 메모리·CDC·영상·주변장치 테스트는 `soc/tools/test_*.sh`와 `soc/tests/`에 있다. 이 게시 작업에서 다시 실행한 검사와 과거 검사 결과는 [검증 문서](검증.md)에서 구분한다.

## 기준본: 실제 Linux 소스 복원

Python 3.12 이상, tar/xz 지원 및 `patch` 명령이 필요하다. 다운로드가 필요하면 버전 고정 URL을 사용하고 SHA256을 검사한다. 기존 소스 폴더를 덮어쓰지 않는다.

```sh
python3 scripts/prepare_linux.py --output /var/tmp/oryukdo-published-source
```

로컬 원본 압축 파일을 지정하려면 `--archive /path/to/linux-6.12.tar.xz`를 추가한다. 전체 수정 소스 압축본을 받았다면 바로 풀어 사용할 수도 있다.

## 기준본: Linux와 SD 이미지 생성

커널 빌드에는 GNU make, host GCC, bison, flex, bc, libssl/libelf 개발 헤더, RISC-V Linux cross GCC, dtc가 필요하다.

```sh
bash scripts/build_linux.sh /var/tmp/oryukdo-published-source/linux-6.12 /var/tmp/oryukdo-published-kernel
```

이 명령은 보존된 init·BusyBox·ddrcheck 실행 파일을 initramfs에 넣고 실제 trace-v2 설정으로 커널을 다시 빌드한다. 새 커널과 보존된 OpenSBI로 SD 이미지를 만들고 내부 페이로드와 CRC를 검사한다. 새 빌드의 비트 단위 동일성이나 실보드 부팅 PASS를 자동으로 보장하지 않는다. 호스트 도구·파일 시간·경로 영향이 있으므로 산출물 해시 및 새 보드 검증을 기록해야 한다.

userspace도 재빌드하려면 `software/userspace/build_busybox.sh /별도/출력경로`를 실행한다. 이 스크립트는 BusyBox·musl 원본 다운로드의 SHA256을 확인한다. 이어서 생성된 `tool/rv32-gcc`로 `init.c`와 `ddrcheck.c`를 `-Os -static -s` 옵션으로 빌드한다. `software/userspace/build_linux.sh`는 과거 일반 커널 빌드용이므로 trace-v2 재현에는 위 `scripts/build_linux.sh`를 사용한다.

OpenSBI 소스는 `riscv-software-src/opensbi`의 위 고정 커밋으로 확보한다. 이번 패키지의 기본 빌드는 검증한 `fw_jump.bin`을 사용한다. OpenSBI를 처음부터 다시 빌드하는 자동 경로와 바이너리 재현성은 이번 게시 준비의 검증 범위에 포함하지 않았다.

Linux를 다시 컴파일하지 않고 검증한 페이로드로 SD를 재구성할 수도 있다.

```sh
python3 soc/board/make_sd.py /var/tmp/oryukdo-published-sd
python3 soc/board/verify_image.py /var/tmp/oryukdo-published-sd/ORYUKDO-Gen3-BOSIO-KFB-1GiB-BusyBox.img software/firmware /var/tmp/oryukdo-published-sd/gen3.dtb
```

## 기준본: Vivado 보드 전체 구현

Windows PowerShell 예시이다. 설치 경로와 짧은 출력 경로를 환경에 맞춘다.

```powershell
& 'D:/Xilinx2202/Vivado/2022.2/bin/vivado.bat' -mode batch -source soc/board/build_mig.tcl -tclargs D:/build/oryukdo-mig
python soc/board/run_board.py D:/build/oryukdo-board --ip D:/build/oryukdo-mig/kfb_bosio_mig.srcs/sources_1/ip/mig_7series_0/mig_7series_0.xci --strategy area-medium-guarded
```

대상 부품은 `xc7a200tfbg484-2`이다. MIG 설정과 핀 배치를 보존하며 공식 HDMI IP를 변경하지 않는다. CPU/fabric 추가 setup uncertainty 0.300ns를 유지한다. 출력 `route` 디렉터리에서 비트스트림과 Setup/Hold·DRC·CDC·배선 보고서를 확인한다.

보존된 실보드 비트스트림은 **area-medium-incremental** 전략으로 이전 routed checkpoint를 참고해 만들었다. 위 명령은 그 과거 checkpoint 없이 새로 구현하는 경로이다. 동일 RTL이어도 배치 결과와 비트스트림 해시가 달라질 수 있다. 현재 보관한 +0.101ns를 새 실행에 그대로 적용하면 안 된다. 배선 후 WNS/WHS≥0, TNS/THS=0과 미배선·오류 없음으로 다시 판단한다.

## 기준본: 전체 RTL 콜드 부팅

```sh
KFB_SD_IMAGE=/path/to/ORYUKDO-KFB-clocksource-trace-v2.img bash soc/board/coldboot/run.sh /var/tmp/oryukdo-published-cold
```

MIG PHY와 HDMI 직렬화는 모델 경계이다. CPU·DDR 상태를 스냅샷으로 주입하지 않고 SD 부트부터 실행한다. 장시간 소요되며 이번 게시 준비에서는 재시작하지 않았다. 기존 전체 RTL 실행이 쉘에 도달한 것으로 보고하지 않는다.
